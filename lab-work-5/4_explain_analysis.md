# Аналіз продуктивності запиту за допомогою EXPLAIN

**Тестовий запит:**
```sql
SELECT * FROM `Products` WHERE `price` = 320.00;
```

---

## 1. План виконання "ДО" створення індексу

**Результат команди `EXPLAIN`:**

| id | select_type | table | type | possible_keys | key | key_len | ref | rows | Extra |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | SIMPLE | Products | ALL | NULL | NULL | NULL | NULL | 10 | Using where |

**Аналіз:**
* У колонці `type` вказано **`ALL`** — це означає повне сканування таблиці.
* Значення `possible_keys` та `key` дорівнюють **`NULL`**, оскільки індекс для колонки `price` відсутній.
* СУБД змушена послідовно переглядати всі 10 рядків у таблиці `Products` (`Using where`), щоб знайти товар із ціною `320.00`.

---

## 2. Створення індексу

```sql
CREATE INDEX `idx_products_price` ON `Products` (`price`);
```

---

## 3. План виконання "ПІСЛЯ" створення індексу

**Результат команди `EXPLAIN`:**

| id | select_type | table | type | possible_keys | key | key_len | ref | rows | Extra |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | SIMPLE | Products | ref | idx_products_price | idx_products_price | 5 | const | 1 | |

**Аналіз:**
* У колонці `type` значення змінилося з `ALL` на **`ref`**.
* У колонках `possible_keys` та `key` відображається створений індекс **`idx_products_price`**.
* Значення в колонці `rows` зменшилося з `10` до **`1`** — оптимізатор одразу звертається до потрібного запису через індекс без перебору всієї таблиці.

---

## Висновок
Створення індексу `idx_products_price` на полі `price` кардинально змінило план виконання запиту: замість повного сканування всієї таблиці `ALL`, сервер бази даних використовує індексний пошук `ref`, що значно підвищує швидкодію вибірки товарів за ціною при зростанні обсягу даних.
